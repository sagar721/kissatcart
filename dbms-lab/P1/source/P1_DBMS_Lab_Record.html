2. Aim

To design an Entity–Relationship (ER) model for a College Management System, map the ER model into a relational schema, and create the corresponding database and tables in PostgreSQL 17 with appropriate primary key, foreign key and integrity constraints.

3. Problem Statement

A college needs to store and manage information about its departments, students, faculty members, the courses offered, and the enrollment of students in those courses. Every student and every faculty member belongs to exactly one department, every course is taught by one faculty member, and a student may enroll in many courses while a course may have many students. For each enrollment, the date of enrollment and the marks obtained must be recorded.

Design an ER diagram that captures these requirements, convert it into a relational schema, and implement the schema as a PostgreSQL database named college_db.

4. Objectives

  1. To identify the entities, attributes and relationships of a real-world system.
  2. To select a primary key for every entity and identify the foreign keys needed to link entities.
  3. To determine the cardinality (1:N, M:N) and participation of each relationship.
  4. To draw the ER diagram using standard (Chen) notation.
  5. To map the ER diagram into a relational schema using standard ER-to-relational mapping rules.
  6. To create the database and tables in PostgreSQL 17 using DDL commands and verify them.

5. Case Study Description – College Management System

The college is organised into departments (for example, Computer Science and Engineering, Artificial Intelligence and Machine Learning). Each department is identified by a department ID and has a unique name.

Students are admitted into a department. For every student the college records a student ID, name, e-mail address (unique for each student) and phone number. Faculty members are also attached to a single department and are identified by a faculty ID.

The college offers courses. Each course has a course ID, a name and a number of credits, and is assigned to one faculty member who teaches it; a faculty member may teach several courses.

Students register for courses. One student can take many courses and one course can be taken by many students, so this is a many-to-many association. Each registration is stored as an enrollment record holding the enrollment ID, the student, the course, the enrollment date and the marks scored (marks may be empty until the course is evaluated). A student cannot enroll in the same course twice.

12. Relational Schema

12.1 Mapping Rules Applied

  1. Strong entities: Department, Student, Faculty and Course each become a table containing their simple attributes; the key attribute becomes the PRIMARY KEY.
  2. 1 : N relationships (Belongs_To, Works_In, Teaches): the primary key of the “1” side is added as a FOREIGN KEY in the table of the “N” side – department_id in student and faculty, faculty_id in course. Because participation of the N side is total, these columns are NOT NULL.
  3. M : N relationship (Student–Course): a separate table enrollment is created. It contains the primary keys of both participating entities as foreign keys (student_id, course_id) and the attributes of the relationship (enrollment_date, marks). A surrogate primary key enrollment_id is used, and UNIQUE (student_id, course_id) preserves the rule that a student enrolls in a course only once.

12.2 Schema (PK underlined, FK in italics)

DEPARTMENT ( department_id, department_name )

STUDENT ( student_id, student_name, email, phone, department_id → DEPARTMENT )

FACULTY ( faculty_id, faculty_name, department_id → DEPARTMENT )

COURSE ( course_id, course_name, credits, faculty_id → FACULTY )

ENROLLMENT ( enrollment_id, student_id → STUDENT, course_id → COURSE, enrollment_date, marks )

13. Explanation of the ER Model

  • Department is the central entity. It takes part in two one-to-many relationships: Belongs_To with Student and Works_In with Faculty. A department may exist before any students or faculty are added (partial participation), but every student and every faculty member must belong to a department (total participation).
  • Faculty and Course are linked by Teaches (1 : N). Each course has exactly one faculty member in charge, so faculty_id is stored in the course table and is NOT NULL.
  • Student and Course have a many-to-many relationship. A relational table cannot store a list of courses in a single student row, so the relationship is modelled as the associative entity Enrollment. Each enrollment row links one student to one course and also holds the facts that belong to that pairing – the enrollment date and the marks.
  • Keys enforce correctness: primary keys prevent duplicate rows, foreign keys maintain referential integrity (an enrollment cannot point to a student who does not exist), UNIQUE prevents duplicate e-mail addresses, department names and repeat enrollments, and CHECK constraints keep credits between 1 and 6 and marks between 0 and 100.
  • Identity columns (GENERATED ALWAYS AS IDENTITY, the SQL-standard replacement for SERIAL in PostgreSQL) generate key values automatically.

14. SQL Commands for Database Creation (PostgreSQL 17)

The commands below create the database college_db and its five tables. Parent tables are created before the tables that reference them.

-- Create the database and connect to it
CREATE DATABASE college_db;
\c college_db

-- Parent table
CREATE TABLE department (
    department_id   INT GENERATED ALWAYS AS IDENTITY,
    department_name VARCHAR(100) NOT NULL,
    CONSTRAINT pk_department PRIMARY KEY (department_id),
    CONSTRAINT uq_department_name UNIQUE (department_name)
);

-- Department 1 : N Student
CREATE TABLE student (
    student_id    INT GENERATED ALWAYS AS IDENTITY,
    student_name  VARCHAR(100) NOT NULL,
    email         VARCHAR(120) NOT NULL,
    phone         VARCHAR(15),
    department_id INT NOT NULL,
    CONSTRAINT pk_student PRIMARY KEY (student_id),
    CONSTRAINT uq_student_email UNIQUE (email),
    CONSTRAINT fk_student_department FOREIGN KEY (department_id)
        REFERENCES department (department_id)
        ON UPDATE CASCADE ON DELETE RESTRICT
);

-- Department 1 : N Faculty
CREATE TABLE faculty (
    faculty_id    INT GENERATED ALWAYS AS IDENTITY,
    faculty_name  VARCHAR(100) NOT NULL,
    department_id INT NOT NULL,
    CONSTRAINT pk_faculty PRIMARY KEY (faculty_id),
    CONSTRAINT fk_faculty_department FOREIGN KEY (department_id)
        REFERENCES department (department_id)
        ON UPDATE CASCADE ON DELETE RESTRICT
);

-- Faculty 1 : N Course
CREATE TABLE course (
    course_id   INT GENERATED ALWAYS AS IDENTITY,
    course_name VARCHAR(100) NOT NULL,
    credits     SMALLINT NOT NULL,
    faculty_id  INT NOT NULL,
    CONSTRAINT pk_course PRIMARY KEY (course_id),
    CONSTRAINT chk_course_credits CHECK (credits BETWEEN 1 AND 6),
    CONSTRAINT fk_course_faculty FOREIGN KEY (faculty_id)
        REFERENCES faculty (faculty_id)
        ON UPDATE CASCADE ON DELETE RESTRICT
);

-- Student M : N Course (associative table)
CREATE TABLE enrollment (
    enrollment_id   INT GENERATED ALWAYS AS IDENTITY,
    student_id      INT NOT NULL,
    course_id       INT NOT NULL,
    enrollment_date DATE NOT NULL DEFAULT CURRENT_DATE,
    marks           NUMERIC(5,2),
    CONSTRAINT pk_enrollment PRIMARY KEY (enrollment_id),
    CONSTRAINT uq_enrollment_student_course UNIQUE (student_id, course_id),
    CONSTRAINT chk_enrollment_marks CHECK (marks BETWEEN 0 AND 100),
    CONSTRAINT fk_enrollment_student FOREIGN KEY (student_id)
        REFERENCES student (student_id)
        ON UPDATE CASCADE ON DELETE CASCADE,
    CONSTRAINT fk_enrollment_course FOREIGN KEY (course_id)
        REFERENCES course (course_id)
        ON UPDATE CASCADE ON DELETE CASCADE
);

16. Result and Conclusion

An ER model for the College Management System was designed with five entities – Department, Student, Faculty, Course and Enrollment – and four relationships: Department 1 : N Student, Department 1 : N Faculty, Faculty 1 : N Course, and Student M : N Course resolved through the Enrollment associative entity. The ER diagram was mapped into a relational schema using standard mapping rules, and the database college_db with all five tables was successfully created in PostgreSQL 17.

The execution output confirms that all primary key, foreign key, UNIQUE and CHECK constraints were created as designed, that data can be joined correctly across all five tables, and that PostgreSQL rejects invalid data (non-existent student, marks above 100, duplicate enrollment, deletion of a referenced department). Hence, the practical was performed successfully.

17. Viva Questions and Answers

Q1. What is an ER model?
The Entity–Relationship model is a high-level conceptual data model that describes the data of a system in terms of entities, their attributes and the relationships among them. It is drawn as an ER diagram and later converted into tables.
Q2. What is the difference between an entity and an entity set?
An entity is a single real-world object that can be distinctly identified, e.g. one particular student. An entity set is the collection of all entities of the same type, e.g. all students; it becomes a table in the relational model.
Q3. What are the different types of attributes?
Simple (atomic) and composite, single-valued and multi-valued, stored and derived, and key attributes. A null-able attribute such as marks may also have no value.
Q4. Define super key, candidate key and primary key.
A super key is any set of attributes that uniquely identifies a row. A candidate key is a minimal super key. The primary key is the candidate key chosen by the designer to identify rows; it cannot be NULL. In student, both student_id and email are candidate keys and student_id is the primary key.
Q5. What is a foreign key and what is referential integrity?
A foreign key is an attribute in one table that refers to the primary key of another table. Referential integrity means every non-null foreign key value must match an existing primary key value in the referenced table, e.g. student.department_id must exist in department.
Q6. What is cardinality? Name its types.
Cardinality (mapping cardinality) is the number of entities of one set that can be associated with entities of another set through a relationship: one-to-one (1:1), one-to-many (1:N), many-to-one (N:1) and many-to-many (M:N).
Q7. What is the difference between total and partial participation?
In total participation every entity of the set must take part in the relationship (shown by a double line), e.g. every student must belong to a department. In partial participation some entities may not take part, e.g. a department may have no students yet.
Q8. How is a 1 : N relationship mapped to tables?
The primary key of the table on the “1” side is placed as a foreign key in the table on the “N” side. For Department 1 : N Student, department_id is added to the student table.
Q9. How is an M : N relationship mapped, and why is the Enrollment table needed?
An M : N relationship cannot be represented by a single foreign key, so a new table is created containing the primary keys of both entities as foreign keys plus any relationship attributes. Enrollment stores student_id, course_id, enrollment_date and marks, converting Student M : N Course into two 1 : N relationships.
Q10. What is an associative entity? Is Enrollment a weak entity?
An associative entity is an entity created to represent an M : N relationship that has its own attributes. Enrollment is not a weak entity here because it has its own primary key (enrollment_id) and does not depend on an owner entity for identification.
Q11. Why is UNIQUE (student_id, course_id) used in the enrollment table?
Because enrollment_id is a surrogate key, it would not by itself prevent the same student from being enrolled in the same course twice. The UNIQUE constraint enforces this business rule and makes (student_id, course_id) an alternate key.
Q12. What does GENERATED ALWAYS AS IDENTITY do?
It makes PostgreSQL automatically generate a unique sequential value for the column on every insert. It is the SQL-standard identity column and is preferred over the older SERIAL pseudo-type. With ALWAYS, users cannot insert their own value unless they use OVERRIDING SYSTEM VALUE.
Q13. What is the difference between ON DELETE CASCADE and ON DELETE RESTRICT?
CASCADE automatically deletes the child rows when the parent row is deleted (deleting a student removes the student's enrollments). RESTRICT refuses to delete a parent row while child rows still refer to it (a department with students cannot be deleted), as shown in Screenshot 9.
Q14. What are DDL and DML? Give examples.
DDL (Data Definition Language) defines the structure of the database: CREATE, ALTER, DROP, TRUNCATE. DML (Data Manipulation Language) works on the data: INSERT, UPDATE, DELETE, SELECT.
Q15. What is a relational schema? Define degree and cardinality of a relation.
A relational schema is the name of a relation together with its list of attributes, e.g. COURSE(course_id, course_name, credits, faculty_id). The degree is the number of attributes (4 for course) and the cardinality is the number of tuples (rows) in the relation at a given time.
